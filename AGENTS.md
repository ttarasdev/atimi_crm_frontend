# Правила роботи з Atimi CRM frontend

## Еталон

- Стиль коду та структура — як у `../residdy_managers_crm`: прочитай його `src/shared/README.md`, робочі `src/app`, `src/components`, `src/api`, `src/features`, налаштування TypeScript, ESLint і Prettier перед нетиповими змінами.
- `src/shared/old-front`, `new-back`, `new-back-2` у Residdy — архівні копії, не основа для нового коду. Не копіюй архіви сюди.
- Візуальний дизайн цього CRM — погоджений файл Figma `ivan_crm` (bbFAg2fya1Fp7OZkX7walL). Для оболонки, списку клієнтів і картки клієнта орієнтир — саме `Page 1` (`Klienci`, node `507:5170`; `Klient / Etapy`, node `487:4990`), а не альтернативні CRM - Desktop / CRM - Mobile. Старий дизайн Residdy CRM неактуальний; `residdy_mobile` може бути лише додатковим візуальним орієнтиром.

## Стек і формат

- Next.js App Router, React, TypeScript strict, npm та `package-lock.json`.
- SCSS Modules поруч із компонентами; загальні tokens і mixins у `src/shared/styles`. Не додавати Tailwind, CSS-in-JS або сторонню UI-систему без окремої потреби.
- 4 пробіли, одинарні лапки, без крапок із комою. Між інструкціями — порожній рядок, між сусідніми import його не потрібно; не більше одного порожнього рядка. Дотримуйся ESLint і Prettier.
- Імена компонентів і файлів компонентів — PascalCase, наприклад `ClientForm.tsx` та `ClientForm.module.scss`. Утиліти й API-файли — kebab-case; використовуй `import type` для типів і alias `@/*` для `src/*`.
- Node 24.20.0 / npm 12.0.2, версія Node у `.nvmrc`.

## Структура

- `src/app` — маршрути, metadata, layouts; page-файли тонкі, складають готові компоненти. `(public)` і `(private)` — групи маршрутів. Назва групи сама по собі не забезпечує авторизацію.
- `src/components/ui` — базові елементи; `form-components`, `layout-components`, `feedback` — форми, оболонки та стани відповідно. Інші групи додавай за реальною потребою, як у Residdy CRM.
- `src/features/<feature>` — предметна логіка і компоненти конкретної функції.
- `src/api/<resource>/<resource>.api.ts` — запити; `<resource>.types.ts` — контракти. Використовуй чинний спільний HTTP-клієнт `src/api/http.ts`.
- `src/shared/config` — налаштування; `providers`, `hooks`, `query`, `guards`, `styles` — спільна інфраструктура.
- Не запроваджуй додаткові repository/use-case/service шари на фронті та не копіюй універсальний каталог Residdy, якщо функції CRM його не потребують.

## React, API та форми

- Server Components за замовчуванням; `use client` лише для hooks, стану, подій і браузерних API.
- Для серверного стану після підключення API використовуй TanStack Query, як в еталоні. Не встановлюй бібліотеки лише для майбутніх функцій.
- Не роби HTTP-запити прямо в UI-компонентах. Типізуй запити й відповіді відповідно до бекенд DTO, без `any` та вигаданих контрактів.
- Query keys розділяють списки, фільтри й деталі; передавай AbortSignal, інвалідуй потрібні кеші після мутацій. Не повторюй мутації автоматично.
- Форми обробляються через `onSubmit`, без дубльованого submit в `onClick`; пов’язані label, відповідний autocomplete, loading, помилки та disabled під час надсилання.
- Public/private asset uploads передають обов’язковий originalName через multipart. Поле назви автозаповнюється file.name; заміна файла оновлює лише порожню чи попередню автоматичну назву, ручну зберігає. Спільний useUploadName забезпечує trim/1–255/no controls і повтор після помилки без втрати назви. Документ клієнта/етапу при новому upload використовує свій title, без дубльованого поля назви. Скачування додає фактичне розширення з MIME; позначку формату не виводимо з назви. Аватар задає назву на сервері, вкладення локальних файлів пошти не створюють асетів.
- Клієнтські guards керують UI, але не захищають серверні дані. Використовуй чинні auth providers/guards і серверні перевірки доступу, без фальшивих сесій і hardcoded токенів. Зміна сесії очищає query cache; приватні дані різних менеджерів не мають змішуватися.
- Публічні змінні середовища не містять секретів. Адреса API визначається через `NEXT_PUBLIC_API_URL` у `src/shared/config/api.ts`.

## Правила саме цього CRM

- Інтерфейс польською, desktop і mobile. На відміну від еталонного CRM, мобільна версія тут потрібна.
- Аватарів у клієнтів немає; вони можливі тільки для менеджерів.
- Розділ меню — `Zarządzanie`; конструктор етапів та галерея іконок — його частини.
- Одна команда, без вибору команди чи multi-tenancy. Менеджер входить у систему, клієнт — окрема сутність.
- Справа створюється з назвою та необов’язковим processTemplateId. Повний шаблон копіює впорядковані етапи разом із задачами, нотатками й документами; копії незалежні від наступних змін шаблону. Без шаблону справа починається без етапів.
- Реалізовані auth, адаптивна оболонка/профіль, клієнти та справи/етапи, конструктор, календар, працівники, особисті нотатки, документи й DOCX-шаблони, leads, partners, пошта, налаштування фірми/сайту, пульпіт і admin-статистика. Галерея management/icons працює з public assets bucket icons: admin додає PNG/WebP та змінює isPopular, менеджер переглядає; видалення у UI немає. Розділу нерухомості немає. `/main/tasks` працює через `/tasks`: компактний список, вкладки часу, стани todo/in_progress/done, незалежний пріоритет і редагування через спільний Popup/FormContainer. Admin має команда/мої та призначення активного працівника; інші — власні завдання. Sender-only відкриває власні внутрішні завдання без клієнтських чи кадрових запитів.
- Для public-іконок використовуй спільний ThemedIcon за iconId; локальний blob preview передається через src. Колір — currentColor/prop color, alpha mask. IconGrid повторно використовується для вибору іконки у формах. Списки/деталі/мутації — через usePublicAssets та спільні query keys.
- Галерея іконок має один спільний список без перемикача всіх/популярних: популярні першими, з червоним бордером і дуже слабким фоном. Плитки 50×50, проміжки 8px. Відступи в нових формах і попапах компактні, стандартно 12–16px.
- Popup — спільний контейнер модальних вікон. Форми складаємо з FormContainer, FormFooter і MediaFileInput; не дублюй їх у наступних функціях. Див. components/form-components/README.md. Заголовок сторінки галереї відсутній; меню й breadcrumb зберігають її назву.
- Підсторінка Zarządzanie/Kalendarz (`/main/management/calendar`) керує шаблонами типів подій через наявний `task-types` API, без окремої таблиці шаблонів і без створення самих подій. Admin створює/редагує/архівує/відновлює, менеджер переглядає. Архівування — PATCH isActive, DELETE немає.
- `/main/management/stages` — конструктор шаблонів етапів через stage-templates і вкладені tasks/notes/documents API/hooks. Метадані: title/iconId/color/description; admin змінює й архівує/відновлює, менеджер переглядає та скачуває документи. Дефолтні задачі мають тип з автоматичним isDefault, назву й опис; без дат, часу, calendarId, isDone та нагадувань. Задачі мають CRUD, підтвердження видалення й reorder up/down. Нотатки — plain text body до 10 000 знаків; документи — title/privateAssetId з client_documents і видимістю team. Списки нотаток/документів мають незалежні пошук і пагінацію; порядку для них сервер не має. Документ редагує лише title, DELETE від'єднує файл. ClientDocumentForm повторно використовуємо з fixedVisibility/team, DocumentLibraryPicker — з bucket/visibility. Скачування йде через авторизований вкладений маршрут шаблону. Копії у справах клієнтів незалежні від змін шаблону; вихідний team-файл шаблону доступний команді й після копіювання.
- `/main/documents` — загальна бібліотека через private-assets з documentsOnly=true: manager_documents, user_documents і client_documents в одному списку, фільтри bucket/ownOnly/visibility, пошук і пагінація. Автор або admin змінює originalName та видимість; перейменування не змінює фізичний UUID/шлях і не відв'язує записи. Доступ до файлів чужих клієнтів перевіряє сервер навіть для team. Використані файли не видаляємо; 409 показуємо зрозуміло. Байти отримуємо авторизовано, формат/назву скачування визначаємо з MIME. DocumentLibraryPicker повторно використовуємо з відповідними дозволеними buckets, ownOnly, visibility і maxFiles; налаштування picker не замінюють серверну авторизацію.
- `/main/management/document-templates`: окремий доступний до створення шаблону каталог системних полів за джерелом (фірма/працівник/клієнт/легалізація/документи/дата) та власних полів із пошуком і копіюванням тегів. Admin заздалегідь створює власне поле з незмінним key, label/defaultValue. Після upload DOCX до 5 MB обов’язковий POST `/document-templates/analyze`: відомі поля показуються за джерелом; невідомі — із підказками й явним створенням власного поля або виправленням DOCX. Немає автоматичної реєстрації невідомих ключів. Заміна файла чи назви скидає аналіз; збереження блокується до аналізу без невідомих полів. Backend повторно перевіряє файл. Upload/retry/cleanup зберігають ручну назву та прибирають лише власний неприв’язаний cached asset.
- `/main/leads` — реальні звернення: пошук, фільтри статусу/джерела, пагінація, ручне створення, внутрішня нотатка, призначення опікуна адміністратором, перетворення на нового або наявного клієнта того самого опікуна. Менеджер працює лише зі своїми зверненнями, admin з усіма; converted-запис зберігає посилання на клієнта. Не підмінюй перевірки сервера локальними фільтрами й не надсилай листів автоматично при перетворенні.
- `/main/partners` — спільний каталог контактів: категорії, місто, пошук, рекомендації й пагінація; рекомендовані першими. Менеджер переглядає активні записи, admin створює/редагує, позначає рекомендованих, архівує/відновлює. Використовуй partners API/hooks, а не локальну демонстраційну колекцію.
- TextInput, FormIconInput, FormColorInput і FormReminderInput — спільні поля форм. Іконки у picker завантажуються через public-assets hooks, популярні першими в одному списку. Колір preview, бордер і слабкий фон беруться з одного значення. Нагадування — до 10 унікальних offset у хвилинах (0–525600); події без часу не надсилають їх за правилами бекенду.
- Дефолтний тип визначається isDefault, автоматично вибирається при створенні події, доступний для редагування та не архівується. Обов'язковий taskTypeId зберігається у БД; бек підставляє дефолтний ID, якщо create body його не містить.
- Власний календар працює з /calendars/me, без вибору працівника. Admin відкриває календар працівника з його картки через /main/managers/[id]/calendar та /calendars/manager/:id; використовуй ті самі компоненти. Desktop — тиждень, mobile — день, обидва мають список і date picker. Події без часу — задачі над шкалою; дедлайни — тонкі лінії. Створення/редагування/перегляд/видалення складаються зі спільного Popup та полів форм. Повторення створюються лише тут; редагування/видалення серій мають one/following/all, пов'язаних записів — local/everywhere.
- FormSelect, FormTextarea, FormDateTimeInput і FormTaskTypeInput повторно використовуй у наступних формах. CalendarStageInput вибирає власного клієнта → справу → відкритий етап. Час у формах і сітці завжди в calendar.timeZone, API передає ISO з offset; datetime-local у часовому поясі браузера не використовуй без перетворення.
- Профіль використовує реальні дані менеджера та PATCH /managers/me через useUpdateMyManager, який оновлює кеш сесії. Редагуються name/surname/phone/position; phone/position очищаються explicit null. remindersEnabled — єдиний загальний перемикач усіх календарних email, зокрема нагадувань етапів. Не вмикай його автоматично при відкритті сторінки. SettingsRow і Switch — спільні компоненти наступних налаштувань; чинне меню зберігається.
- Desktop-меню згортається до вузької смуги іконок із доступними назвами; mobile зберігає чинний drawer. Шкала календаря 08:00–24:00, ранні записи доступні в «Przed 8:00»; шапка й часова сітка мають спільну ширину та прокрутку.
- ManagerAvatar повторно використовуй для профілю, хедера й меню. Приватні байти отримуй через авторизовані hooks, не прямий img URL без Bearer; blob URL звільняй, помилка фото показує ініціали. POST/DELETE /managers/me/avatar повертає профіль і оновлює кеш сесії; bucket manager_avatars уже є, використовується private variant.
- Профільні зміни email/пароля потребують currentPassword і завершуються лише після листів. Email — підтвердження обох адрес, пароль — поточної. Публічні /auth/confirm-email-change та /auth/confirm-password-change відправляють token лише кнопкою, auth:false, з no-referrer. Після завершення очищуй сесію й показуй /auth?updated=email|password; після першого email-підтвердження сесія залишається. Не змінюй реальні облікові дані під час тестів; використовуй підмінені API та окрему тестову БД.
- Чинний UI використовує погоджений Page 1: світле тло й меню, синій #2563EB, pill-кнопки, компактні нейтральні картки та слабкий кольоровий фон. Повторно використовуй shared tokens/components; не повертай старий стиль заглушок.

## Запуск і перевірки

- `npm run dev` — `http://localhost:4200`; `npm run start` — та сама адреса після `npm run build`.
- Бекенд — `http://localhost:4201`; `.env.example` містить адресу API. `.env.local` та секрети не комітити.
- Перед завершенням: `npm run lint`, `npm run typecheck`, `npm run build`, `npm run format:check`. Для змін UI перевіряй відповідні розміри екрана.
- Пиши тести для поведінки, коли вона з’явиться; не додавай тести, що лише повторюють стартову заглушку.
- Playwright перевіряє desktop/mobile з підміненими API, без змін робочої БД та реального SMTP. Знімки QA конструктора: /tmp/ivan-stage-template-content-shots; DOCX-шаблонів: /tmp/ivan-document-templates-shots. Це тимчасові артефакти поза репозиторієм.

Один classic-дизайн має мови pl/en/ua, default pl. Каталог містить language/previewSubject/previewText для прикладу в preview; вибір мови не змінює ручну тему, текст чи preset. Shared presets створює/редагує/видаляє admin у Zarządzanie, особисті — власник із composer. Перед відправленням тему й текст можна адаптувати. Вкладення й перевірки повторно використовуються в обох формах; перегляд не надсилає листів.
- `/main/company` використовує singleton `/company-settings`: team переглядає, admin змінює назву, юридичні дані, контакти, сайт і logoPublicAssetId з public bucket system_files. Нові листи й preview беруть актуальні дані фірми; персональний підпис ручного листа — із профілю авторизованого менеджера. SMTP-відправники налаштовуються окремо. Не змінюй реальну пошту/контакти під час тестів і не надсилай тестових листів.
- Active-етап справи відрізняється від вибраного для перегляду: лише active має суцільний кольоровий фон, вибраний неактивний — слабкий фон і рамку. Стрічка центрує active при відкритті справи, зміні активного, порядку та ширини; крайні етапи також центруються завдяки боковим відступам. Scrollbar прихований; стрілки й свайп працюють. Завершення active переходить до наступного active зі списку й залишає справу відкритою. Метадані етапу редагує лише admin; менеджер може переміщувати вліво/вправо, видаляти порожній відкритий етап і працювати з його вмістом.

## Atimi / Atlantis

- CRM — Atimi, логотип і контакти — Atlantis. Польський інтерфейс, desktop/mobile. Домен `atimi.pl`; локальні фронт `4200`, API `4201`. Production `NEXT_PUBLIC_API_URL=https://atimi.pl/api` фіксується під час build; секрети в браузер не передавати.
- Три ролі: admin (усе), manager (власні клієнти та читання чужих неприватних), sender (незалежне право на розсилки). Одиночна пошта доступна всім працівникам; кампанії — admin/sender. Sender-only відкриває `/main/tasks`, `/main/mail`, `/main/mail/campaigns` і профіль; не показувати навігацію до клієнтської бази. При створенні працівника roleNames за замовчуванням `['manager', 'sender']`, можна залишити лише sender. Зміни ролей — наявний PATCH з roleIds.
- Client.isPrivate=true за замовчуванням. Власник/admin змінює, інші менеджери лише читають public-клієнта й вкладені записи. Read-only застосовувати до справ, етапів, контактів, нотаток, файлів, карт і родини. Не запитувати календар чужого опікуна для public read-only клієнта. Admin може передати клієнта через PATCH managerId; календарні нагадування переносить сервер.
- Дані легалізації: GET/PATCH `/clients/:id/legalization`, групи особистих даних, адрес, перебування, роботи/навчання. Порожні рядки очищають необов’язкові значення. emailMarketingConsent нового клієнта стандартно true, emailAutomationConsent лишається false; явні відмови зберігаються; маркетингові розсилки беруть лише emailMarketingConsent=true.
- Картки: системний `/document-card-types` без create/delete; admin PATCH reminderMonths/reminderTime/notificationEmail. GET/POST/PATCH `/clients/:id/document-cards`; дата expiresAt, необов’язкові number/issuedAt/notes та статус active/replaced/archived. Стандартні нагадування 3/2/1 календарний місяць; admin може задати інші 1–24. Сервер створює події календаря опікуна, стандартно 09:00 Europe/Warsaw. Заміна/архів скасовують майбутні нагадування. Не дублювати створення подій на фронті.
- Календарні події з clientCardId керуються карткою: показувати пояснення та посилання clientId, приховати generic edit/delete/mark done. Не змінювати системні події напряму.
- `DigitalDocumentCard` — спільний візуал цифрових документів для картки клієнта, живого preview форми та системного каталогу. 13 дизайнів визначаються `type.code`, персональні дані — з профілю клієнта; без аватарів, вигаданих номерів, державних печаток і MRZ. `isStayBasis` явно вибирає власник/admin для поточного документа побиту; прапорець не визначається за строком і не перебудовує нагадування. Read-only приховує редагування.
- Родина: `/clients/:id/relations` parent/spouse/sibling. Parent create означає поточний клієнт є батьком/матір’ю вибраного. API direction описує спорідненість relatedClient до відкритого клієнта. Зворотний зв’язок створює сервер; не дублювати записи. Самого клієнта приховувати в picker; недоступних приватних родичів API не повертає.
- `/process-templates`: title/description/stageTemplateIds/isActive, admin змінює, manager читає. Порядок редагується у списку; створення справи передає processTemplateId. caseData у справі містить serviceType,office,referenceNumber,submittedAt,fingerprintsAt,decisionAt,collectionAt, дати YYYY-MM-DD.
- `/clients/duplicates` дає неблокувальні збіги контактів, PESEL та паспорта з поточним ACL; excludeClientId виключає себе. Не робити власну копію всієї бази для порівняння й не розкривати приватні збіги.
- `/clients/:id/activity` — історія змін (хто/дія/назви полів, без значень). `/mail/history` — власна історія кожного працівника/admin усі, `/clients/:id/mail/history` — історія доступного клієнта. Історія не містить inbox. Генерація DOCX для клієнта потребує writableOnly у FormClientInput.
- Категорії партнерів: notary,legal,translation,accounting,employment,education,insurance,other. Старих категорій нерухомості в нових формах немає.
- Форма завжди submit через onSubmit; допоміжним кнопкам усередині форм явно задавати type="button". Перед завершенням lint/typecheck/format:check/build і релевантні Playwright desktop/mobile; mock API не надсилає реальних листів. Після QA зупинити власний dev-сервер4200. Знімки нових екранів `/tmp/atimi-frontend-shots`.

- Intro має серверний inline-перехід до hydration та клієнтський fallback із native location.replace. Не замінювати його лише useEffect/router.replace: при недоступних початкових JS заставка зависає. Ключ токена брати з ACCESS_TOKEN_STORAGE_KEY. Перевіряти tests/intro-navigation.spec.ts із заблокованими початковими chunks, наявною сесією й недоступним localStorage.

- Розсилки Atimi `/main/mail/campaigns`: доступ admin/sender, manager без sender не відкриває. Admin має всіх неархівних клієнтів, решта — лише клієнтів із managerId поточного працівника; sender-only не отримує доступу до чужої бази. Використовуй `/mail-campaigns` API та окремі accounts/templates/preview. Кампанія пропонує тільки default app@atlantis.info.pl; contact/gmail приховані, preview передає account, сервер повторно перевіряє SMTP-ідентичність. Одиночна пошта зберігає інші скриньки. Пагіновані generic id/label для фільтрів бери тільки з `/mail-campaigns/filter-options?kind=source|stage|manager`; опікуни доступні лише admin, основні CRM API для sender не розширюються. Фільтри status/priority/paymentStatus/sourceId/stageTemplateId/managerId/search; зміна фільтрів скидає підтвердження одержувачів. Перед створенням потрібен preview зі згодою на маркетинг; без одержувачів створення заборонене. Дата/час Europe/Warsaw → ISO; локальна зона браузера не визначає відправку. Спільний MailMessageComposer зберігає direct send та використовує бібліотечні вкладення для кампаній. Список і прогрес опитуються; скасування зупиняє очікування, поточний SMTP не відкликається. Повтор мережевої спроби використовує той самий requestId.

- Картка оплати клієнта: праворуч у картці клієнта, на mobile перед основним вмістом однією колонкою. Ручні paymentAmount (загальна сума, необов’язкова), paymentCurrency (ISO 4217, default PLN), paymentStatus (`unpaid`/`partial`/`paid`, default `unpaid`) та plain-text paymentComment до 2000 знаків. Оплачено — зелений, частково — жовтий, не оплачено — червоний. Admin/власник змінюють через спільний Popup/FormContainer і PATCH `/clients/:id`; null/порожній коментар очищує поле. Чужий спільний або архівний клієнт — read-only; ACL перевіряє сервер. Фільтр клієнтів за paymentStatus серверний. Суми аналітики admin розділяються за валютою; для часткової оплати точний отриманий платіж і залишок не визначаються з коментаря.
- На сторінці клієнта перемикач розсилок використовує існуючий emailMarketingConsent через legalization API/hooks. Для нового клієнта default true, змінюють відповідальний/admin; старі явні false зберігаються; для чужого спільного/архівного клієнта read-only. Зберігається один спільний стан із формою легалізації.
- Запит документа у вкладці документів створює відповідальний/admin без файла, копіює публічне посилання, може оновити або відкликати його. Сторінка /upload-document доступна без входу, приймає token лише з fragment, API auth:false, no-referrer; показує лише назву/інструкцію запиту й форму одного файла. Завантаження створює звичайний приватний документ. Сповіщення відповідального доступні через дзвіночок; sender-only їх не запитує. Переданий приватний клієнт не з’являється у старого відповідального через історичне сповіщення.
- Глобальний пошук у header використовує `/search` і `/search/:type`: debounce 300 мс, групи по три результати, розгортання з пагінацією, скасування застарілих запитів. Sender-only його не відкриває. Посилання ведуть до конкретного запису через client/process/stage/note або ID деталей, які завантажуються окремим GET незалежно від першої сторінки списку. Закриття деталей очищує query, щоб той самий результат можна було відкрити повторно.
- Згадки `@` у нотатках клієнта/етапу використовують доступних адресатів `/clients/:id/note-mentions/recipients`, клавіатурний/мишинний вибір і `mentionedManagerIds`. Підпис зберігається в `mentions`; текст виводиться без HTML. Згадки не надають доступу. Спільний дзвіночок об’єднує `/note-mention-notifications` із документними сповіщеннями, повторює невдале позначення прочитаного й відкриває точну нотатку; sender-only ці API не запитує.
- Календар підтримує зустріч із часом, задачу на день без часу та задачу на весь тиждень без дня/часу. `weekStart` — понеділок Europe/Warsaw; окремий блок над календарем є у day/week/list, без крапки на понеділку. Для тижневих задач лише щотижневі повторення та без SMTP-нагадувань. Admin відкриває вибраний календар працівника й створює всі три види записів; сервер перевіряє доступ.

- Форми задач надсилають `dueDate/dueTime` у Europe/Warsaw лише при зміні терміну; без часу термін до кінця дня. Прив’язки client/stage редагуються явно, зміна відповідального потребує повторної перевірки зв’язку. Для client-assignee дозволений чинний власник із manager або admin; sender-only отримує тільки внутрішні задачі. `canEdit/canDelete` бере сервер; закриті/архівні зв’язки, зустрічі, тижні й серії не редагуються цим CRUD. Статус/видалення/редагування інвалідує tasks, client-stage-records, calendars і crm-overview. Активний список оновлюється кожні 60 секунд без фонового polling. Календар показує точний dueAt для денної задачі, не створює окремий Deadline.

Внутрішній код української мови та API — `ua` (клієнти, звернення, ключі translations, поштові template ID/language). Старі поштові URL `uk`/`uk-*` відкривають український шаблон і надсилають canonical `ua`. Для стандартного HTML lang та Intl використовуємо явне відображення `ua` → `uk`.
